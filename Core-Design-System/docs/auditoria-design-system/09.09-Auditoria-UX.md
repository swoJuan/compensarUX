# 09.09 — Auditoría UX del Sistema de Diseño Compensar

**Producto auditado:** Compensar Design System v2.1.0 (Medicina Prepagada)
**Alcance:** Sistema de diseño completo — tokens, fundamentos y componentes web transversales del `core/`
**Métodos:** Auditoría heurística (10 heurísticas de Nielsen) + Auditoría de accesibilidad (WCAG 2.2 · principios POUR)
**Fecha:** Agosto 2026
**Evaluador:** OneClickUX (expert review)

---

## Nota metodológica y de alcance

Esta auditoría es una **revisión experta (expert review)** sobre el código fuente del sistema de diseño (`core/`), sus tokens y sus componentes. No reemplaza el testing con usuarios reales ni con tecnologías asistivas.

Los siguientes puntos **no se pueden validar solo desde el CSS/tokens** y quedan marcados como pendientes de verificación manual:

- `[PENDIENTE: validación manual]` Focus trap, cierre con ESC y retorno de foco en Modal (dependen del JS de integración, documentados en `ia-context.md` pero no presentes en `core/`).
- `[PENDIENTE: validación manual]` Comportamiento real con lectores de pantalla (NVDA / JAWS / VoiceOver).
- `[PENDIENTE: validación manual]` `aria-live` / `role` en Loading, Toast y Alert (el CSS los prevé pero dependen del HTML productivo).

Los ratios de contraste se calcularon sobre los valores hex de `core/abstracts/_tokens-colors.scss` y `core/base/_theme.scss`. Se recomienda confirmarlos con una herramienta automatizada (axe, WAVE, DevTools) antes de cerrar cada fix.

## Resumen ejecutivo

El sistema de diseño de Compensar tiene una **base de accesibilidad y arquitectura notablemente sólida**: theming por tokens (Light / Dark / High Contrast) alineado a Figma, `:focus-visible` global, soporte de `prefers-reduced-motion`, `forced-colors`, áreas táctiles de 44px y patrones `aria-disabled` consistentes. El modo Alto Contraste está bien resuelto.

Los problemas se concentran en **dos frentes**: (1) **contraste de la marca naranja** sobre blanco, que afecta al componente más usado del sistema (botón primario) y a los enlaces; y (2) **deuda de consistencia** por convivencia de APIs nuevas (`mp-*`) y legacy (`.btn`, `.input`, `.check-wrap`), que se traduce en radios, grosores de foco y estilos divergentes.

## Lo que funciona bien (refuerzo positivo)

Documentar los aciertos es parte de la auditoría y ayuda a no romperlos en futuros cambios:

- **Theming por tokens semánticos** — Los componentes consumen `var(--use-*)` y nunca hex directos; el cambio de tema no requiere lógica por componente. Arquitectura correcta.
- **Foco visible global** — `:focus-visible { outline: 2px solid ... }` en `_accessibility.scss` + rings de 3px en componentes nuevos.
- **`prefers-reduced-motion`** — Implementado global y además Loading tiene fallback específico (ralentiza en vez de matar la animación). Cumple WCAG 2.3.3.
- **Áreas táctiles 44px** — `.mp-choice` (hit 44×44), `.mp-switch` (min-height 44px), utilidad `.touch-target`. Cumple WCAG 2.5.5/2.5.8.
- **Alto Contraste robusto** — Bordes blancos visibles, negro puro, foco amarillo, `--color-text-disabled` elevado a `#b8b8b8` para cumplir sobre negro.
- **`forced-colors: active`** contemplado para iconos.
- **No depender solo del color** — Alertas/toasts combinan icono + texto + borde; se documenta `role="status"` vs `role="alert"`.
- **Dark mode alineado a Figma** con tokens de marca ajustados (`#ff9d5c`) para no perder contraste.

# Parte A — Auditoría Heurística (Nielsen)

## H1 · Visibilidad del estado del sistema

### NN-01-H1 · El estado loading del botón legacy oculta el label accesible
- **Severidad:** 2 (Menor)
- **Ubicación:** `core/components/web/_buttons.scss` → `.btn-loading`
- **Descripción:** `.btn-loading` aplica `color: transparent !important` para ocultar el texto y mostrar solo el spinner `::after`. Visualmente correcto, pero durante la carga el usuario pierde toda referencia textual de qué acción está en curso, y el spinner `::after` no tiene texto alternativo.
- **Heurística:** H1 (Visibilidad) + solapamiento con accesibilidad.
- **Recomendación:** Mantener el texto para lectores de pantalla y anunciar el cambio de estado. El componente nuevo `.mp-btn--loading` (que anima el icono sin ocultar el texto) es mejor patrón; unificar hacia él.
```html
<!-- Preferir el patrón mp-btn: el icono gira, el texto permanece -->
<button class="mp-btn mp-btn--primario mp-btn--loading" aria-busy="true" disabled>
  <span class="material-symbols-rounded" aria-hidden="true">progress_activity</span>
  Guardando…
</button>
```

### Observación (positiva)
Loading, Toast y Alert están preparados para feedback de estado. Verificar en el HTML productivo que Toast use `aria-live="polite"`, Alert de error use `role="alert"` y el spinner de página exponga `role="status"` con texto. `[PENDIENTE: validación manual]`

---

## H2 · Correspondencia con el mundo real

### NN-02-H2 · Labels en mayúsculas fijas reducen legibilidad
- **Severidad:** 1 (Cosmético)
- **Ubicación:** mixin `ty-label` (`text-transform: uppercase`) usado por `.field-label`.
- **Descripción:** Los labels de formulario legacy van en mayúsculas por el mixin. El texto todo-mayúsculas es más lento de leer y puede afectar a usuarios con dislexia. El input nuevo `.mp-input-label` ya usa capitalización normal (Roboto Regular 16px), lo cual es más legible.
- **Recomendación:** Migrar labels de formulario al patrón `.mp-input-label`. Reservar `uppercase` para eyebrows/overlines, no para labels de campo.

---

## H3 · Control y libertad del usuario

### NN-03-H3 · Cierre y salida de Modal no verificables desde el core
- **Severidad:** 3 (Mayor) — condicionado a verificación
- **Ubicación:** `core/components/web/_modals.scss` + `ia-context.md`.
- **Descripción:** El CSS del modal define el botón de cierre (`.mp-modal__close`) y el overlay, pero el comportamiento de "salida de emergencia" (cerrar con ESC, click en backdrop, focus trap, retorno de foco) es responsabilidad del JS de integración, que no vive en `core/`. `ia-context.md` lo documenta como requisito, pero no hay implementación de referencia.
- **Heurística:** H3 (Control y libertad) + WCAG 2.1.2 (No keyboard trap) inverso.
- **Recomendación:** Publicar un JS de referencia mínimo en la capa reutilizable acordada (o un ejemplo en la doc del modal) que garantice: cierre con ESC, focus trap mientras está abierto y retorno de foco al disparador. Añadir al checklist QA la validación por teclado. `[PENDIENTE: validación manual]`

---

## H4 · Consistencia y estándares

### NN-04-H4 · Doble API de componentes (mp-* vs legacy) — deuda de consistencia
- **Severidad:** 3 (Mayor)
- **Ubicación:** Botones, inputs y selection-controls conviven en dos APIs:
  - Botón: `.mp-btn` (nuevo, español) **y** `.btn` / `.btn-primary` / `.btn-ghost`... (legacy, mezcla ES/EN).
  - Input: `.mp-input-field` (nuevo) **y** `.input` / `.field` / `.select` (legacy).
  - Selección: `.mp-choice` (nuevo, control custom) **y** `.check-wrap` / `.toggle` con `accent-color` nativo (legacy).
- **Descripción:** Aunque `ia-context.md` declara `.mp-*` como fuente de verdad y legacy solo como compatibilidad, ambas están activas en `core.css`. Un consumidor puede tomar el patrón equivocado y obtener estados, radios y foco distintos. Esto es exactamente la violación que Nielsen H4 busca evitar: la misma acción con dos comportamientos.
- **Recomendación:**
  1. Marcar formalmente la API legacy como *deprecated* con comentario en cada partial y fecha de retiro.
  2. Publicar una tabla de migración (`.btn-primary` → `.mp-btn .mp-btn--primario`, etc.).
  3. Plan de retirada por versión (p.ej. eliminar en v3.0.0).
  4. Mientras convivan, alinear tokens compartidos (radio, foco) para minimizar divergencia visual.

### NN-05-H4 · Radios de esquina inconsistentes entre APIs
- **Severidad:** 2 (Menor)
- **Ubicación:** `.mp-btn` usa `--radius-md` (24px); legacy `.btn` usa `$radius-xs`. `.mp-input-field` usa 16px hardcodeado (`rem(16px)`) mientras legacy `.input` usa `$radius-xs`.
- **Descripción:** Dos botones o dos inputs de la misma pantalla pueden verse con curvaturas distintas según la API. Además `.mp-input-field` fija `16px` en vez de consumir `--radius-*`, saltándose el sistema de tokens de radio.
- **Recomendación:** Consumir siempre tokens de radio. Definir un token `--radius-input` y `--radius-btn` semánticos y usarlos en ambas APIs.

### NN-06-H4 · Grosor de foco inconsistente (2px vs 3px)
- **Severidad:** 2 (Menor)
- **Ubicación:** `_accessibility.scss` global usa `outline: 2px`; el mixin `focus-ring` usa `2px`; los componentes nuevos usan `var(--color-focus-ring-width: 3px)`.
- **Descripción:** El anillo de foco cambia de grosor según el elemento. Rompe la consistencia del indicador de foco, que debe ser predecible en todo el producto.
- **Recomendación:** Unificar a `var(--color-focus-ring-width)` (3px) en el reset global y en el mixin `focus-ring`. Un solo token gobierna el grosor.

## H5 · Prevención de errores

### NN-07-H5 · Input requerido depende del asterisco de color
- **Severidad:** 2 (Menor)
- **Ubicación:** `.field-label .required` y `.mp-input-required` (asterisco en color de error).
- **Descripción:** La obligatoriedad se comunica con un asterisco coloreado. Si el HTML no incluye además el atributo `required`/`aria-required` y un texto accesible, el estado no es percibible por todos ni prevenido por el navegador.
- **Recomendación:** Acompañar el asterisco con `required aria-required="true"` en el input y con texto accesible (`aria-label="obligatorio"` en el asterisco o `<span class="sr-only">obligatorio</span>`). Documentarlo como regla obligatoria en el checklist QA de inputs.

---

## H6 · Reconocimiento en lugar de recuerdo

### NN-08-H6 · Riesgo de usar placeholder como único label (API legacy)
- **Severidad:** 2 (Menor)
- **Ubicación:** `.input::placeholder` (legacy) + patrón `.input-wrap`.
- **Descripción:** El sistema define placeholders con color tenue. Si en implementación se usa el placeholder como sustituto del label (patrón común), el label desaparece al escribir y el usuario pierde el contexto — obliga a recordar en vez de reconocer.
- **Recomendación:** Reforzar en la doc que el label siempre es visible y persistente (el patrón `.mp-input-group` con `.mp-input-label` ya lo hace bien). Prohibir explícitamente placeholder-como-label en el checklist QA.

## H7 · Flexibilidad y eficiencia

### Observación
- **Severidad:** 1 (Cosmético / mejora)
- El sistema de diseño no expone aceleradores (atajos de teclado documentados, acciones batch). Es esperable en una **librería de componentes** (los aceleradores viven en el producto, no en el DS), por lo que no se penaliza. Recomendación de mejora: documentar en la guía de cada componente interactivo qué teclas debe soportar (Tabs → flechas; Modal → ESC; Dropdown → flechas + Esc), para que los productos lo implementen de forma consistente.

---

## H8 · Diseño estético y minimalista

### NN-09-H8 · Paleta muy amplia con riesgo de tokens sin uso
- **Severidad:** 1 (Cosmético)
- **Ubicación:** `_tokens-colors.scss` — familias `product/teal`, `product/violet`, `base/green-2`, `base/cyan-blue`, `base/orange` con 5–11 escalones cada una.
- **Descripción:** La paleta primitiva es extensa. Sin un mapa claro de qué escalón semántico usa cada primitivo, hay riesgo de tokens huérfanos y de que dos diseñadores elijan tonos distintos para el mismo propósito (ruido sistémico, contrario a H8).
- **Recomendación:** Ejecutar un **token audit** (skill `ux-design-token-audit`): marcar cada primitivo como "usado por token semántico X" o "sin uso". Los primitivos sin alias semántico ni consumo deberían archivarse o justificarse.

# Parte B — Auditoría de Accesibilidad (WCAG 2.2 · POUR)

## Perceptible (Perceivable)

### A11Y-01 · Botón primario: contraste texto/fondo insuficiente
- **Severidad:** 4 (Crítico)
- **WCAG:** 1.4.3 Contraste (Mínimo) — AA
- **Ubicación:** `.mp-btn--primario` y `.btn-primary` — texto blanco `#ffffff` sobre gradiente `#ff6600 → #e63f0c`.
- **Descripción:** En el tope del gradiente (`#ff6600`, `base-brand-80`), el contraste con blanco es **≈ 2.9:1**. El texto de botón es 16px/700 → es "texto normal" salvo que se considere bold ≥ 18.66px; a 16px bold NO califica como large text, por lo que el umbral es **4.5:1**. Falla. En la parte baja (`#e63f0c`) sube a ≈ 4.6:1, pero como el gradiente es vertical, la mitad superior del label queda bajo el umbral. Es el componente más usado del sistema.
- **Impacto:** Usuarios con baja visión, daltonismo o pantallas con brillo bajo/sol directo no leen con fiabilidad la acción principal.
- **Recomendación:** Oscurecer el naranja de acción para texto blanco. Opciones:
  - **A (recomendada):** Usar `#e63f0c` (`base-brand-90`, ≈4.6:1) como color base del botón primario, con gradiente hacia `#cc5200` (`base-brand-100`). Conserva identidad y cumple AA.
  - **B:** Mantener el naranja de marca pero con **texto oscuro** (`#111111`) sobre él (≈ 4.8:1 sobre `#ff6600`) — cambia la estética.
```scss
// Opción A — gradiente que cumple AA con texto blanco
.mp-btn--primario {
  --mp-btn-bg: linear-gradient(180deg, var(--use-primary-hover) 0%, var(--use-primary-active) 100%);
  // #e63f0c → #cc5200 ; texto blanco ≈ 4.6:1 y 5.9:1
  --mp-btn-color: var(--use-text-on-dark-primary);
}
```
> Nota: verificar el resultado con herramienta automatizada, dado que es un gradiente (medir el punto más claro).

### A11Y-02 · Enlaces de texto con color de marca insuficiente
- **Severidad:** 4 (Crítico)
- **WCAG:** 1.4.3 Contraste (Mínimo) — AA
- **Ubicación:** `--use-text-link: var(--base-brand-80)` = `#ff6600` sobre fondo blanco.
- **Descripción:** Un enlace de texto en `#ff6600` sobre blanco da **≈ 2.9:1**, por debajo del 4.5:1 requerido para texto. Además, si el enlace se distingue del texto normal solo por color, incumple 1.4.1 (Uso del color).
- **Impacto:** Enlaces poco legibles y difíciles de identificar como interactivos.
- **Recomendación:**
  1. Definir un token de enlace accesible: `--use-text-link: var(--base-brand-90)` (`#e63f0c`, ≈4.6:1) o `base-brand-100` (`#cc5200`, ≈5.9:1).
  2. Añadir `text-decoration: underline` a enlaces en contenido para no depender solo del color (1.4.1).

### A11Y-03 · Placeholder usa color de estado disabled
- **Severidad:** 3 (Mayor)
- **WCAG:** 1.4.3 Contraste — AA
- **Ubicación:** `.input::placeholder { color: var(--color-text-disabled); }` → `#a4a4a4` (`base-neutral-50`) sobre blanco.
- **Descripción:** El contraste del placeholder es **≈ 2.5:1**. Cuando el placeholder comunica información (formato esperado, ejemplo), debe cumplir 4.5:1. El input nuevo `.mp-input-field` ya usa `--use-text-tertiary` (`#666`, ≈5.7:1) para placeholder — correcto. El problema es solo la API legacy.
- **Recomendación:** Cambiar el placeholder legacy a `var(--use-text-tertiary)` (`#666666`) y no depender nunca del placeholder para instrucciones críticas.
```scss
.input, .select, .textarea {
  &::placeholder { color: var(--use-text-tertiary); } // #666 ≈ 5.7:1
}
```

### A11Y-04 · Texto deshabilitado con contraste muy bajo (informativo)
- **Severidad:** 2 (Menor)
- **WCAG:** 1.4.3 exime a elementos deshabilitados, pero es una barrera de usabilidad real.
- **Ubicación:** `.mp-btn:disabled` → texto `#a4a4a4` sobre fondo `#cccccc` ≈ **1.6:1**.
- **Descripción:** Técnicamente conforme (los inactivos están exentos), pero un botón deshabilitado casi ilegible dificulta entender por qué no se puede actuar. En Light el disabled es muy tenue.
- **Recomendación:** Subir el texto disabled a `base-neutral-70` (`#666`) sobre `base-neutral-20` (`#e0e0e0`) para acercarse a ~3:1 sin sugerir que es accionable. Complementar el estado disabled con motivo textual cuando el bloqueo no sea obvio.

## Operable

### A11Y-05 · Estado de carga sin nombre accesible (botón legacy)
- **Severidad:** 3 (Mayor)
- **WCAG:** 4.1.2 Nombre, función, valor · 1.4.1 Uso del color (indirecto)
- **Ubicación:** `.btn-loading { color: transparent !important; }`
- **Descripción:** Al volver el texto transparente, el botón pierde su nombre accesible visible durante la carga y no se anuncia el cambio de estado. (Ver también NN-01-H1.)
- **Recomendación:** Usar `aria-busy="true"` durante la carga, conservar el texto (patrón `.mp-btn--loading`) o exponer un `aria-label` estable. Nunca comunicar "cargando" solo con un spinner sin texto asociado.

### A11Y-06 · Focus trap / retorno de foco en modal no implementado en core
- **Severidad:** 3 (Mayor) — condicionado a verificación
- **WCAG:** 2.4.3 Orden del foco · 2.1.2 Sin trampa de teclado
- **Ubicación:** Modal (comportamiento en JS de integración).
- **Descripción:** Igual que NN-03-H3, desde accesibilidad: sin focus trap el usuario de teclado puede tabular "fuera" del modal hacia el fondo bloqueado; sin retorno de foco pierde su posición al cerrar.
- **Recomendación:** Referencia JS con focus trap, ESC y retorno de foco; `role="dialog"`, `aria-modal="true"`, `aria-labelledby`, `aria-describedby` (ya documentados en `ia-context.md`). `[PENDIENTE: validación manual]`

## Comprensible (Understandable)

### A11Y-07 · Mensajes de error deben anclarse al campo
- **Severidad:** 2 (Menor)
- **WCAG:** 3.3.1 Identificación de errores · 3.3.3 Sugerencia ante errores
- **Ubicación:** `.field-error-msg` / `.mp-input-helper.error`.
- **Descripción:** El CSS de error existe y es correcto (color + peso). Falta garantizar la asociación programática entre el mensaje y el input.
- **Recomendación:** En el HTML, vincular con `aria-describedby` el input y su mensaje de error, y usar `aria-invalid="true"`. Los mensajes deben decir qué pasó y cómo resolverlo. Añadir al checklist QA.
```html
<input class="mp-input-field error" aria-invalid="true" aria-describedby="e-doc">
<p id="e-doc" class="mp-input-helper error" role="alert">
  El número de documento debe tener entre 6 y 10 dígitos.
</p>
```

## Robusto (Robust)

### TOK-01 · Token `--use-state-info-body` referenciado pero inexistente
- **Severidad:** 3 (Mayor)
- **WCAG:** relacionado con 1.4.3/1.4.1 en tema Dark/HC.
- **Ubicación:** `_alerts.scss` y `_toasts.scss` usan `var(--use-state-info-body, #0b3954)`; ese token **no está definido** en `_tokens-colors.scss` ni en `_theme.scss`.
- **Descripción:** El fallback literal `#0b3954` salva el render en Light, pero como no es un token, **no se sobreescribe en Dark ni en High Contrast**. En esos temas el cuerpo de la alerta/toast info puede quedar con un azul muy oscuro sobre fondo oscuro (bajo contraste), mientras que el título sí cambia porque usa un token real. Es una inconsistencia de theming que puede producir texto ilegible en Dark/HC.
- **Recomendación:** Definir el token en las tres capas de tema (o hacer que `body` de info apunte al mismo token que `title`, como ya hacen success/warning/error). Ejemplo mínimo:
```scss
// en $tokens-light y en cada override de tema
'use/state/info/body': var(--base-blue-100),   // Light
// [data-theme='dark']  --use-state-info-body: #f5f5f5;
// [data-theme='high-contrast'] --use-state-info-body: #ffffff;
```
Alternativa rápida y consistente: en `.mp-alert--info` / `.mp-toast--info`, apuntar `--mp-alert-body` a `--use-state-info-text` (igual que los demás estados).
